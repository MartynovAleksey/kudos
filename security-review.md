# Отчёт по ревью безопасности — kudos

- **Дата:** 2026-07-26
- **Область ревью:** изменения ветки `develop` относительно `origin/main` (весь диапазон доработок `179a5a4…9d73ce1`, ~добавленный код приложения), плюс сканирование Java-зависимостей на известные CVE, включая транзитивные.
- **Модель угроз приложения (важно для трактовки находок):** каждый аутентифицированный пользователь действует под **своей** Kerberos-идентичностью через `UserGroupInformation.doAs`; авторизацию по данным выполняет сам кластер (HDFS/Ozone/HBase/Kyuubi). Поэтому «пользователь может обратиться к своим данным / выполнить произвольный SQL» — это **штатное поведение редактора**, а не уязвимость. Ищутся: обход аутентификации, эскалация до чужой/суперпользовательской идентичности, межпользовательское воздействие (stored XSS, CSRF), инъекции с пересечением границы доверия, утечки секретов/PII.
- **Как читать:** каждая находка — отдельная пронумерованная строка в таблице ниже; подробности и рекомендации по исправлению — в разделах `V1…V5`. Правьте точечно по номерам.

## 2. Детализация находок

### V1 — CSRF отключён на изменяющих состояние `/api/**` эндпоинтах (Medium)

**Файл:** [LdapSecurityConfig.java:96](src/main/java/com/k8spark/ui/security/LdapSecurityConfig.java:96) (`apiSecurity`, `.csrf(csrf -> csrf.disable())`).

**Описание.** Цепочка фильтров для `/api/**` отключает CSRF и одновременно **переиспользует session-cookie** формы входа (`SessionCreationPolicy.NEVER`, но существующая сессия принимается — см. комментарий в коде и `uiSecurity`). Значит, изменяющие состояние запросы (`/api/hbase/table/delete`, `/api/hdfs/delete`, `/api/hdfs/upload`, `/api/hbase/bulk`, `/api/hbase/cell/upload`, `/api/ozone/*` и т.д.) аутентифицируются автоматически передаваемой cookie и не требуют CSRF-токена.

**Сценарий эксплуатации.** Залогиненный пользователь открывает вредоносную страницу. Для JSON-эндпоинтов (`@RequestBody`) атака гасится: `Content-Type: application/json` вызывает CORS-preflight, а CORS-конфигурации нет → браузер блокирует. Однако **multipart-эндпоинты** (`/api/hdfs/upload`, `/api/ozone/upload`, `/api/hbase/bulk`, `/api/hbase/cell/upload`) принимают `multipart/form-data` — это «простой» для CORS тип, preflight не выполняется:

```js
fetch('https://kudos/api/hbase/bulk?table=victimtable',
      { method:'POST', credentials:'include', body: formDataWithCsv });
```

Ответ атакующий не прочитает (SOP), но **побочный эффект** (запись строк в HBase, заливка файла в HDFS/Ozone от имени жертвы) наступит.

**Существенное смягчение.** Современные браузеры по умолчанию трактуют cookie без явного атрибута как `SameSite=Lax`, что **не отправляет** cookie на кросс-сайтовый `fetch`-POST. Приложение явно `SameSite` не задаёт, то есть защита сейчас держится только на дефолте браузера. Поэтому реальная эксплуатируемость — средняя (зависит от браузера/конфигурации), но опираться на неявный дефолт как на единственный барьер — фрагильно.

**Рекомендация.**
1. Явно задать атрибут session-cookie: `server.servlet.session.cookie.same-site=strict` (или `lax`).
2. Для cookie-аутентифицированных запросов включить защиту от CSRF: либо CookieCsrfTokenRepository/токен, либо требовать кастомный заголовок (например, `X-Requested-With`), который кросс-сайтовая простая форма выставить не может. HTTP Basic-путь для скриптов при этом не затрагивается.

### V2 — Не-санитизированный ввод в query-строке WebHDFS (Low)

**Файл:** [HdfsService.java:94](src/main/java/com/k8spark/ui/service/HdfsService.java:94) (`setPermission`), также `delete`/`setOwner` формируют строку операции конкатенацией.

**Описание.** Значение `permission` подставляется в query-строку WebHDFS напрямую: `webhdfs(path, "SETPERMISSION&permission=" + permission)`. В отличие от `destination`/`owner`/`group` (они прогоняются через `URLEncoder.encode`), `permission` не кодируется и не валидируется как восьмеричное. Пользователь может внедрить дополнительные query-параметры (например `permission=755&op=DELETE`).

**Почему Low.** Запрос выполняется в `kerberos.asLoggedInUser(...)`, то есть **от имени самого пользователя**; WebHDFS применит его собственные права. Пользователь и так имеет прямые эндпоинты на все эти операции — внедрение «лишнего» `op` не даёт ничего, чего он не может сделать легально. Пересечения границы доверия нет.

**Рекомендация.** Валидировать `permission` регуляркой `^[0-7]{3,4}$` и/или кодировать все динамические сегменты query-строки через `URLEncoder.encode`, как это уже сделано для остальных параметров. Дешёвая защита «в глубину».

### V3 — Инъекция Spark/Kyuubi-conf в JDBC-URL сессии (Low)

**Файл:** [KyuubiService.java:212](src/main/java/com/k8spark/ui/service/KyuubiService.java:212) (`sessionUrl`).

**Описание.** Пользовательский `sparkParams` разбивается по строкам и вставляется в hive-conf часть JDBC-URL (`;key=value`) без проверки ключей. Значение может само содержать `;`, добавив произвольные conf (например `...=x;hive.server2.proxy.user=admin` или `spark.driver.extraJavaOptions=...`).

**Почему Low.**
- Хост в URL фиксирован конфигом и стоит **до** `?`, подменить его вставкой conf нельзя.
- `proxy.user` эффективен только если аутентифицирующийся принципал сконфигурирован как Hadoop proxy-superuser; обычный пользователь таковым не является → impersonation отклоняется KDC/Hadoop.
- Управление `spark.*` (в т.ч. запуск произвольного кода на движке Spark) — это в рамках **собственной** идентичности пользователя, которую он и так реализует через SQL-редактор. Эскалации нет.

**Рекомендация.** Валидировать ключи по allow-list (`spark.*`, `kyuubi.*`), запретить `;` в значениях и явно отвергать `*proxy.user*`/`principal`/`auth` — чтобы исключить как случайную порчу строки подключения, так и любые будущие сценарии, где принципал приложения окажется proxy-superuser.

### V4 — Подробные сообщения об ошибках отдаются клиенту (Low)

**Файл:** [application.yml:9](src/main/resources/application.yml:9) — `server.error.include-message: always`.

**Описание.** Spring включает текст исключения в тело ответа об ошибке. Сообщения сервисов содержат внутренние детали (например, `"WebHDFS DELETE returned 403: ..."`, пути кластера, тексты исключений JDBC), что помогает атакующему в разведке.

**Рекомендация.** Для production вернуть к `on-param`/`never` либо выдавать обобщённые сообщения, а детали писать только в лог. Это осознанный компромисс ради UX редактора — но стоит явно закрепить его отдельно для боевого профиля.

### V5 — Выход из системы по `GET /logout` (Low / Informational)

**Файл:** [LdapSecurityConfig.java:181](src/main/java/com/k8spark/ui/security/LdapSecurityConfig.java:181) — `logoutRequestMatcher(new AntPathRequestMatcher("/logout"))` принимает GET.

**Описание.** GET-logout принят намеренно (ссылка в сайдбаре и авто-выход по таймеру тикета). Побочный эффект — logout CSRF: сторонняя страница может через `<img src=".../logout">` принудительно завершить сессию пользователя.

**Почему Info.** Импакт низкий (навязанный выход, без утечки данных). Достаточно осознанного принятия риска. Если потребуется устранить — оставить GET только для внутреннего таймера, а публичный logout перевести на POST с CSRF-токеном.

| **Авторизация между пользователями** | Все действия исполняются под личной Kerberos-идентичностью; изоляцию обеспечивает кластер. `FeatureGate` лишь скрывает отключённые модули (не механизм авторизации между пользователями). |

## 4. Сканирование Java-зависимостей на CVE

### 4.1. Методология и ограничения

- Использованный источник версий: `mvn dependency:tree` (полное дерево, включая транзитивные) — 257 узлов.
- В окружении **нет** SCA-сканера с БД NVD (`trivy`/`grype`/`osv-scanner`/OWASP `dependency-check` не установлены), а OWASP DC требует загрузки всей базы NVD и API-ключа. Поэтому таблица ниже — **сопоставление точных версий с известными CVE по состоянию знаний на янв. 2026**, а не вывод автоматического сканера. Перед релизом обязательно прогнать авторитетный SCA (команды — в §4.3).
- **Критическое ограничение охвата:** несколько зависимостей — «толстые»/shaded-джары, которые прячут свои внутренние версии от `dependency:tree`:
  - `org.apache.hive:hive-jdbc:standalone:4.0.1` (бандлит десятки компонентов Hive/Hadoop/логгеров внутри jar),
  - `org.apache.hbase.thirdparty:hbase-shaded-protobuf/netty/miscellaneous/gson:4.1.10`, `hbase-unsafe`,
  - `org.apache.hadoop.thirdparty:hadoop-shaded-protobuf_3_25 / hadoop-shaded-guava:1.4.0`.

  Их содержимое `dependency:tree` не раскрывает — для полноты **нужен бинарный SCA по собранному jar** (`trivy`/`grype` по артефакту), иначе уязвимости внутри shaded-классов будут пропущены.

### 4.4. Рекомендации по зависимостям

1. **Прогнать авторитетный SCA по собранному артефакту** (обязательно — из-за shaded-джаров §4.1). Пример:
   ```bash
   mvn -DskipTests package
   trivy fs --scanners vuln target/kudos-0.1.0.jar
   # или
   grype target/kudos-0.1.0.jar
   ```
2. **Встроить SCA в CI** (OWASP dependency-check либо Trivy/Grype) с падением сборки на High/Critical.
3. Обновить/переопределить в `dependencyManagement`: `commons-compress → 1.26.0+`, `guava → 32.0.1-jre+`, `woodstox-core → 6.4.0+`; по возможности убрать/изолировать legacy `protobuf-java:2.5.0` (тянется HBase — проверить, реально ли используется незашейженный путь).
4. Отслеживать **EOL-компоненты**: Jetty 9.4.x, Jersey 1.x (`com.sun.jersey:1.19.4`), `jsp-api:2.1` — приходят из Hadoop-клиента; при обновлении Hadoop они уйдут.
5. Проверить содержимое `hive-jdbc:standalone:4.0.1` бинарным сканером отдельно — это наибольшая «слепая зона».
